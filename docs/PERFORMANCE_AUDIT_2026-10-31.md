## Вывод

Главная доказанная избыточная работа находится в отрисовке поля. Dirty state уже устранил повторное построение command buffer в один кадр, но сохранённый `Graphics` всё ещё обрабатывается Phaser каждый кадр: разбор команд, создание точек/путей, триангуляция и отправка геометрии. Большое неподвижное поле продолжает делать эту работу без жестов и частиц.

Второй класс проблем — ненужная активность скрытого результата и незавершённое уничтожение спящего Phaser. Признаков неограниченного накопления DOM, обработчиков, worker и звуковых голосов в проверенных обычных переходах не обнаружено. Это не гарантия отсутствия любых утечек на любом Android: измерялись конкретные сценарии, отдельно JS heap и WebGL handles, без native RSS/GPU-memory profiler.

## Метод и ограничения

- Закреплённые зависимости проекта, Phaser 4.2.1; production Vite build приватной копии исходников.
- Единственное изменение копии: доступ к существующим объектам для измерений. Инструменты оборачивают методы и считают вызовы/время; в обычный production build никакие globals не добавлены.
- Chromium headless, 390×844 CSS px, DPR 2, WebGL через ANGLE/SwiftShader. CPU ×4 — искусственная нагрузка, не модель конкретного телефона.
- Тайминги включают накладные расходы instrumentation, а software GPU и автоматизация могут давать выбросы. Это CPU time отдельных участков, не input-to-photon latency и не обещание FPS.
- Простое поле, сложное поле на старте и с префиксом 20 клеток, реальные drag/reverse, победа, варианты без искр/конфетти, повторные переходы, сохранения, worker cancellation, dispose в работающем и спящем состоянии, resize на паузе.
- Сохранения подготовлены локально. Вызовы `WinMotion.start/collect/stop` в отдельном component stress не выдаются за заработанные награды или естественное прохождение банка.
- Во время таймингов не делались скриншоты и не запускался CPU sampling profiler. Allocation sampling выполнялся отдельно с учётом собранных GC объектов; его числа статистические.

## 1. P1: готовое поле заново превращается в геометрию каждый кадр

[BoardScene.update/renderBoard](../src/game/BoardScene.ts#L50) и установленный `phaser/src/gameobjects/graphics/GraphicsWebGLRenderer.js` / `renderer/webgl/renderNodes/FillPath.js`.

| Состояние | Построений command buffer | Вызовов FillPath на кадр Graphics | Синхронный Graphics, медиана / p95 |
|---|---:|---:|---:|
| `intro-01`, старт | 0 в окне замера | 15 | 0,4 / 1,2 мс |
| `shapes-29`, старт | 0 | 108 | 2,9 / 4,9 мс |
| `shapes-29`, префикс 20 | 0 | 377 | 5,4 / 7,3 мс |
| Тот же префикс, CPU ×4 | 0 | 377 | 25,3 / 36,2 мс |

У сложного префикса 16 472 числовых записи command buffer. Это длина массива, **не** количество draw calls. FillPath вызван 377 раз на кадр; кроме него есть StrokePath и прямоугольники. FillPath заново вызывает Earcut. Graphics renderer также создаёт объекты точек кривых; даже маленькие окружности и скругления проходят общий векторный путь.

Диагностическое скрытие Graphics обнуляет эти вызовы, хотя остаются движок и номера. Это доказывает источник работы, но скрытое поле не является приемлемой оптимизированной версией игры.

### Allocation churn

Две отдельные sampling-выборки неподвижного префикса:

- Около 103 МБ оценённых выделений за 19 Graphics-кадров; без Graphics — около 1,2 МБ за сопоставимое время.
- Около 275 МБ за 48 Graphics-кадров; без Graphics — около 0,9 МБ.

Порядок величины — **5–6 МБ временных выделений на Graphics-кадр** в этих выборках. Sampling включает другие задачи страницы и не является точным счётчиком каждого байта. Основные allocation stacks сопоставлены с кодом `GraphicsWebGLRenderer`, `FillPath`, `StrokePath`, batching и Earcut. Это поток временных объектов, а не 275 МБ удерживаемой памяти. Он создаёт условия для GC-пауз, однако длительность каждой конкретной паузы здесь не атрибутирована.

**Что делать:** перестать прокручивать Phaser loop при действительно неподвижном поле; пробуждать его на изменение состояния/ввод/локальный FX/resize. Затем отделить статическую основу, изменяемый маршрут и маленький FX-слой. Кешировать готовое изображение или геометрию вместо повторной триангуляции: текущие поле/тема/размер, с ограниченным числом ресурсов. Для победы по возможности анимировать готовую фигуру, а не заново строить всю её геометрию.

Нельзя просто отключить RAF: должны сохраниться первый быстрый жест, head halo, завершение FX, resize во сне и destruction. Любой cache требует явной инвалидации и ограничения памяти; не кешировать все 90 полей во всех темах. Не менять Phaser/vendor ради обхода без отдельной причины. WebGL RenderTexture и подготовленные меши/спрайты — варианты реализации, а не уже проверенное ускорение; выбрать на реальном A/B с сохранёнными градиентами и маркерами.

## 2. P2: скрытый результат продолжает анимироваться

[CSS результата](../src/style.css#L77), [частичное блокирование ambience](../src/style.css#L236), [видимость экранов](../src/main.ts#L148).

После победы → домой Phaser loop уже спит, частицы/монеты очищены. Однако `getAnimations()` показывает 11 running CSS animations с `visibility: hidden`: 7 букв, 3 звезды и подпись Next. В результате DOM visibility не останавливает анимационный timeline. В синтетическом visibility-blocker ambience и эмблема становятся paused, а эти 11 остаются running.

Это активный timeline; браузер может пропускать отрисовку невидимых объектов, поэтому существенная CPU/GPU-стоимость этих 11 анимаций отдельно не доказана. Это **не доказательство растущей утечки** и не измерение расхода батареи в реальном Android background: браузер/ОС могут дополнительно ограничивать невидимую страницу.

**Что делать:** связать CSS-анимации результата с активным экраном и общими блокировками, аналогично ambience. Останавливать или приостанавливать скрытые сцены. Не заменять `visibility` на `display:none` без проверки геометрии и ResizeObserver: текущий layout рассчитывается и для сохранённого поля.

## 3. P2: teardown спящего Phaser не завершается

[dispose()](../src/main.ts#L497) вызывает `game.destroy(true)` после остановки собственных сервисов. В установленном Phaser этот метод только устанавливает `pendingDestroy`; реальное уничтожение выполняется на следующем game step.

| Сценарий | Через 500 мс после dispose |
|---|---|
| Loop работал | `pendingDestroy=false`, canvas 0, textures 0, RAF/interval/worker 0, AudioContext закрыт |
| Loop спал после выхода домой | `pendingDestroy=true`, остаётся 1 canvas и 4 Phaser textures |
| Диагностически разбудить второй случай | `pendingDestroy=false`, canvas 0, WebGL context ресурсы уничтожены |

**Что делать:** гарантировать завершение публичного Phaser destruction и наблюдать `DESTROY`; освобождать ownership в согласованном порядке. Проверить работающую игру, меню, паузу/фон, ранний запуск и HMR. Не вызывать приватный `runDestroy()` вслепую.

Граница риска: воспроизведён отдельный вызов полного dispose в приватном harness. В production он вызывается на уходе страницы, где уничтожается и JS realm; HMR — development. Из этого нельзя заключать, что обычное открытие меню накапливает новый renderer. Но текущий cleanup-контракт при повторной инициализации неверен.

## 4. Частицы: есть улучшения, но массовое урезание не обосновано

[WinMotion.draw](../src/presentation/motion.ts#L121), [BoardScene FX](../src/game/BoardScene.ts#L38).

- В естественной победе измерен пик 330 confetti; source cap 360. Draw 2D в одной выборке: медиана около 0,6 мс, p95 около 1,4 мс. Это JS/canvas submission, без полной стоимости GPU raster/compositing.
- После выхода в меню particles/coins/timers/WAAPI collections обнуляются. Бесконечной очереди эмиттеров в проверенных сценариях не найдено.
- Искры ограничены 36. В drag-выборках пик 18–24. После прогрева выполнена последовательность baseline → no-sparks → no-sparks → baseline. Медианы Graphics: примерно 3,8–4,2 против 3,5–3,6 мс. p95 заметно колеблется, устойчивого крупного выигрыша по хвостам не установлено.
- Вариант no-sparks убирает искры после `react`, поэтому не исключает первоначальное создание их объектов; он изолирует преимущественно последующую отрисовку. Это не полный low-FX mode.
- Даже без искр остаётся примерно 179 FillPath на кадр в этой короткой drag-траектории против 186–188 с ними. Главная стоимость поля не исчезает.

**После основного рендера:** precomputed unit paths/Path2D для звёзд и треугольников, меньше повторной тригонометрии, reusable particle storage и уплотнение массива вместо `filter` на каждом кадре. Рассмотреть отдельный DPR budget для FX только после визуального сравнения. Начальная burst-скорость/кадровый шаг и жизнь particles требуют сохранения общего ритма.

Не выдавать эти небольшие идеи за гарантированный большой эффект. Сохранять богатую победу; число частиц уменьшать по измерениям, а не потому, что оно выглядит большим в исходнике.

## 5. P2–P3: ввод и сохранения

[gesture](../src/core/gesture.ts), [layout](../src/ui/layout.ts), [flush](../src/main.ts#L215), [writer](../src/services/save.ts#L69).

Hit-test перебирает все клетки, строит временные прямоугольники/массивы, сортирует пересечения; геометрия bounds вычисляется повторно. При максимуме около 30 клеток это вторичный кандидат. Кеш layout/cell bounds до resize/смены поля проще и полезнее, чем новый пространственный индекс. Сегментный ввод/последовательный reverse нельзя заменять выбором ближайшей клетки.

Store синхронно сериализует, валидирует progression и drafts и снова сериализует snapshot. Синтетический benchmark 60 повторных записей одинакового prefix:

| Save | Медиана / p95 | CPU ×4, медиана / p95 |
|---|---:|---:|
| Начальный, 320 символов | около 0,1 / 0,5 мс | около 0 / 1,0 мс |
| 90 заполненных drafts, около 9 КБ | 0,8 / 1,8 мс | 2,7 / 4,7 мс |

Нулевые округлённые измерения не означают нулевую стоимость. Это microbenchmark с подготовленным большим save, а не доказательство таких пауз на каждом pointermove. Пауза/возобновление без изменения пути восемь раз действительно вызвала восемь одинаковых save writes.

**Что делать позже:** не сохранять неизменённый обычный prefix повторно, кешировать безопасные derived content-данные. Сохранять ownership/conflict checks, durable first-clear/gift/wheel и строгую проверку при загрузке. Не переводить ценные операции в coalesced очередь ради оптимизации.

## 6. Память и ресурсы: что проверено

В первом soak после прогрева: 38 реальных UI-циклов «задача → победа → меню», затем 20 отдельных presentation stress cycles со сбором/отменой монет.

- В сопоставимом состоянии main menu: 414 DOM nodes, 65 JS listeners, 1 document во всех контрольных точках.
- Очереди particles, coins, motion timers/animations, sparks: 0. Ghost copies: 0. Приложение держит один interval календаря; активного Phaser RAF в меню нет.
- Один AudioContext на сессию, 0 оставшихся голосов. Контекст закрывается при dispose.
- 20 worker requests: 10 найденных ответов + 10 явных отмен, активных workers после завершения 0.
- JS heap после forced GC: от 5,66 до 6,14 МБ decimal; после component stress около 6,18 МБ. Малый рост сам по себе не доказывает ни утечку, ни её отсутствие: возможны прогрев JIT/engine caches. Дополнительный длинный soak записан в evidence отдельно.
- Дополнительный независимый soak: **102 UI-цикла**. После forced GC JS heap от 5.40 до 5.95 МиБ; за последние 12 циклов +2792 bytes. DOM/listeners всё время 414/65, оставшихся voices/workers/RAF в меню 0. Это соответствует выходу на плато, а не явному runaway; небольшой рост не атрибутирован конкретным retained objects.
- WebGL resource soak: 30 смен размера на паузе после прогрева. 10 live textures, 9 buffers, 2 programs и 4 shaders во всех точках; роста handles не найдено. Счётчики WeakRef не удерживают ресурсы намеренно. Изменение размера GPU allocation внутри того же handle этим не измеряется.

Не найдено оснований говорить «все ресурсы гарантированно чистые» или «Android не будет лагать». Проверки сужают поиск; выявленный sleeping-dispose дефект остаётся отдельной задачей.

## Порядок оптимизации и приёмка

1. **Основной рендер и покой.** Убрать повторную триангуляцию статичного изображения; разделить основу/маршрут/FX; безопасный sleep/wake. Сравнить CPU submission и allocation bytes на кадр на одинаковых поле/префиксе/DPR. Скрытое поле из аудита не считать готовым A/B.
2. **Полная остановка/освобождение.** Довести CSS gates и teardown. Должны проходить dispose при running/sleeping/background, без оставшегося canvas/GL; обычные переходы не накапливают DOM/listeners/worker/voices. Сохранить repaint при resize на паузе.
3. **Частицы и вторичные расчёты.** Precomputed paths/пулы, затем layout/color/save cache только по профилю. Сначала сохранить нынешний внешний вид и наградный ритм.
4. **Физический Android.** Длинное быстрое движение по сложному полю, reverse/release/resume, полный win/collect, пауза/фон/resize, серия повторов. Измерить кадры, задержку, native memory и температуру/энергопотребление. Browser numbers не являются этим этапом.

Никаких новых зависимостей, переписывания стека, обновления vendor, снижения качества всех тем или сокращения банка для этой работы не требуется.

## Повторение замеров

Из корня репозитория, после `npm ci` и установки Playwright Chromium:

```bash
node tools/performance-audit.mjs
node tools/performance-audit.mjs --supplement
node tools/performance-audit.mjs --drag-repeats
node tools/performance-audit.mjs --long-soak
```

Выполнять последовательно: параллельные benchmark-процессы и DevTools recording искажают wall timings. Harness создаёт только игнорируемую `.test-output/performance-audit/probe-src`, собирает приватную production-копию и открывает собственный preview. `--supplement` измеряет allocation sampling/WebGL handles/identical pause writes; `--drag-repeats` — порядок ablations после прогрева; `--long-soak` — более длинную серию UI cycles. Raw profiles остаются в `.test-output`; компактная evidence сохранена в docs.
